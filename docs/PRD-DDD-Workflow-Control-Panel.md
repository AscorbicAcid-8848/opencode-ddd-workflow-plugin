## 1. 文档信息

| 项目 | 内容 |
|---|---|
| 产品名称 | DDD Workflow 控制面板 |
| 所属产品 | OpenCode DDD Workflow Plugin |
| 文档状态 | Draft |
| 目标版本 | v0.3.0 |
| 主要入口 | `/ddd-workflow` |
| 目标用户 | 使用 DDD Workflow Plugin 的产品经理、领域专家、架构师和开发人员 |

## 2. 需求摘要

在当前项目中增加一个由 OpenCode Plugin SDK 实现的 Slash 命令控制面板。用户输入 `/ddd-workflow` 后，直接进入全屏 TUI 控制面板，并在面板内部查看、筛选和操作本项目所有 DDD workflow，包括正在进行、等待人工审核、阻塞、待归档和已经完成归档的 workflow。

控制面板不仅展示阶段状态，还要把六个人工审核里程碑中已经形成的业务与设计结论转换成容易理解的可视化视图，例如战略事件流、子域分类、限界上下文关系、战术事件流、聚合结构、纵向切片和最终证据覆盖情况。

控制面板由 SDK 直接读取工作流状态和持久化产物，不通过 LLM 生成页面。打开、筛选、切换和刷新面板不产生模型调用与 Token 消耗。

## 3. 背景与问题

当前 DDD 工作流已经能够维护三类互斥流程：已有系统新增功能、遗留系统重构和新系统创建。每个流程包含六个人工审核里程碑，并在 `openspec/changes` 中持续保存状态、阶段产物、正式里程碑文档和归档记录。

但用户仍然面临以下问题：

1. 不容易知道当前项目有多少个 workflow，哪些仍在进行，哪些已经完成；
2. 必须进入较深的 OpenSpec 目录才能找到里程碑文档；
3. Markdown 适合保存完整结论，但不适合快速理解事件先后、边界关系和交付进度；
4. 用户无法在同一个界面比较“已批准”“待批准”“要求修改”和“尚未开始”的里程碑；
5. 工作流状态、人工决定、业务模型和实现证据分散，缺少统一入口；
6. 如果使用普通 Prompt 命令生成状态报告，会增加 Token 消耗，并可能由模型错误解释持久化状态。

## 4. 产品目标

### 4.1 核心目标

1. 通过一个 Slash 命令打开项目级 DDD workflow 控制面板；
2. 同时发现活动 change 和 archive 中的历史 change；
3. 清楚展示每个 workflow 的类型、状态、当前阶段、人工审核进度和下一步动作；
4. 为 I 至 VI 六个人工里程碑提供与阶段语义匹配的可视化；
5. 严格区分已批准结论、待人工确认方案、候选项、未决问题和已经验证的实现事实；
6. 允许用户从控制面板进入人工审核，但不得绕过现有状态机和门禁；
7. 面板展示不依赖 LLM，不修改正式文档，不产生模型 Token。

### 4.2 非目标

首个版本不负责：

- 在控制面板中编辑完整里程碑正文；
- 用 LLM 根据 Markdown 临时生成图；
- 替代 OpenSpec 的变更、校验和归档能力；
- 替代现有 `/ddd` 与 `/ddd-code` 命令；
- 跨多个本地项目建立组织级管理后台；
- 把限界上下文自动转换为微服务；
- 在缺少结构化数据时猜测领域事件、聚合或上下文关系。

## 5. 用户角色与核心场景

### 5.1 产品经理或领域专家

- 查看当前有哪些需求正在进行 DDD 分析；
- 快速阅读事件流、子域和限界上下文；
- 找到等待自己确认的里程碑；
- 批准方案或指出需要修改的业务结论。

### 5.2 架构师

- 查看战略设计与战术设计是否逐级收敛；
- 检查上下文关系、数据所有权、聚合边界和模块依赖；
- 对比多个历史 change 对领域边界的影响。

### 5.3 开发人员

- 查看当前允许实施的纵向切片；
- 从里程碑 IV、V 定位模型、代码路径、测试与回滚要求；
- 查看实现是否已经通过里程碑 VI 和 OpenSpec 归档。

## 6. 入口与命令设计

### 6.1 主命令

```text
/ddd-workflow
```

命令行为：

1. 使用 SDK 注册的 TUI Slash Command；
2. 直接打开名为 `ddd-workflow` 的全屏 TUI Route；
3. 不向当前会话提交 Prompt；
4. 不调用模型和 `ddd_lifecycle`；
5. 默认显示当前项目的全部 workflow；
6. 搜索、筛选、排序、打开指定 workflow 和切换里程碑全部在控制面板内部完成。

### 6.2 单一入口约束

- `/ddd-workflow` 不接收命令参数；
- 不提供 `/ddd-dashboard`、`/ddd-status` 等别名；
- 不通过参数区分 active、review、blocked 或 completed；
- 所有导航和过滤操作由 TUI 控件承担；
- 每次执行该命令都进入同一个项目级控制面板，并恢复用户上次在面板中的位置与筛选状态。

## 7. 信息架构

控制面板采用“项目总览、Workflow 详情、里程碑详情”三层结构。

```text
DDD Workflows
├── 项目总览
│   ├── 全部
│   ├── 待我审核
│   ├── 进行中
│   ├── 阻塞
│   └── 已完成
├── Workflow 详情
│   ├── 基本信息与进度
│   ├── 六里程碑时间线
│   ├── 当前下一步
│   └── OpenSpec / Git / 验证状态
└── 里程碑详情
    ├── 当前结论
    ├── 阶段专属可视化
    ├── 未决问题与 AI 建议
    ├── 证据与追踪
    └── 人工审核操作
```

## 8. 项目总览需求

### 8.1 顶部摘要

显示以下统计信息：

- Workflow 总数；
- 等待人工审核数量；
- 正在进行数量；
- 阻塞数量；
- 待归档数量；
- 已完成或已归档数量。

### 8.2 Workflow 列表

每一项至少显示：

| 字段 | 说明 |
|---|---|
| 标题 | Workflow 的业务名称 |
| Workflow ID | 对应 OpenSpec change ID |
| 类型 | 新增功能、系统重构或新建系统 |
| 状态 | 进行中、待审核、要求修改、阻塞、待归档、已完成 |
| 当前里程碑 | I 至 VI |
| 当前阶段 | 当前阿拉伯数字内部阶段 |
| 人工进度 | 已批准里程碑数，例如 `3/6` |
| 下一步 | 继续建模、等待审核、修订、编码、归档等 |
| 更新时间 | 最近一次状态事务时间 |
| OpenSpec 状态 | 活动 change、待归档或已归档 |

### 8.3 排序和过滤

- 默认顺序：待人工审核、阻塞、进行中、待归档、已完成；
- 同一状态内按照最后更新时间倒序；
- 支持按 Workflow ID、标题和原始需求搜索；
- 支持按 workflow 类型和当前里程碑过滤；
- 已归档 workflow 默认折叠，但始终可以访问。

### 8.4 状态颜色

| 状态 | 颜色语义 |
|---|---|
| 待人工审核 | 黄色 |
| 正在进行 | 蓝色 |
| 已批准 / 已完成 | 绿色 |
| 要求修改 | 橙色 |
| 阻塞 / 拒绝 | 红色 |
| 未开始 / 历史信息 | 灰色 |

不得只依靠颜色表达状态，必须同时显示文字和图标。

## 9. Workflow 详情需求

### 9.1 顶部信息

显示：

- Workflow 标题、ID 和类型；
- 原始用户请求；
- 创建时间、更新时间和完成时间；
- 当前状态、当前阶段和下一步；
- OpenSpec change 路径和归档状态；
- 当前会话绑定信息；
- 若存在阻塞，展示阻塞原因、证据和恢复建议。

### 9.2 六里程碑时间线

固定展示 I 至 VI，不因 workflow 尚未到达后续阶段而省略。

每个里程碑显示以下状态之一：

- 尚未开始；
- AI 正在形成阶段产物；
- 等待人工审核；
- 已批准；
- 要求修改；
- 已拒绝；
- 已被后续版本替代；
- 已完成并归档。

点击里程碑进入里程碑详情。尚未开始的里程碑只显示输入条件，不生成虚构内容。

## 10. 六个人工里程碑的可视化要求

### 10.1 里程碑 I：战略事件风暴

主要视图：端到端业务事件流。

必须展示：

- 参与者；
- 命令；
- 过去时领域事件；
- 策略与业务规则；
- 读模型；
- 外部系统和时间触发器；
- 正常路径、拒绝路径、异常和补偿；
- 热点、边界线索和未决问题；
- 对已有系统重构，标识 AS-IS 事实、候选解释和行为保护约束。

建议形式：可横向滚动的泳道时间线。节点按照 EventStorming 类型使用稳定颜色，并提供图例。

### 10.2 里程碑 II：战略设计

主要视图：子域、限界上下文和 Context Map。

必须展示：

- 核心子域、支撑子域和通用子域，并使用三种固定颜色；
- 每个限界上下文的职责、非职责、通用语言和数据所有权；
- 子域与限界上下文之间的映射；
- 上下文的上下游方向、协作契约和防腐策略；
- 限界上下文与单体模块、应用或微服务的工程承载关系；
- 实现单元用例包；
- 历史战略决策的复用、修改、新增和冲突情况。

建议形式：左侧子域分类卡片，中央限界上下文边界图，右侧上下文关系图。不得把限界上下文默认画成微服务。

### 10.3 里程碑 III：战术事件风暴

主要视图：一个已批准实现单元内的 Design-Level EventStorming。

必须展示：

- 命令、策略、领域事件和读模型的追踪关系；
- 正常流程、业务拒绝、技术失败、补偿和恢复；
- 不变量候选、并发热点和事务边界候选；
- 聚合、领域服务和读模型候选；
- 持久化热点与外部依赖；
- 需要回退里程碑 II 的跨边界问题。

建议形式：上下文边界内的事件流程图，并通过虚线连接候选模型和热点。

### 10.4 里程碑 IV：战术设计

主要视图：领域模型与用例实现结构。

必须展示：

- 应用服务及其命令、查询和事务边界；
- 聚合根、实体和值对象的层级；
- 聚合行为、不变量和状态转换；
- 领域服务、领域事件、仓储和工厂；
- 模型到持久化、缓存、投影和集成适配的映射；
- 接口层、应用层、领域层和基础设施层的依赖方向；
- 模型、不变量和测试的追踪关系。

建议形式：聚合树、用例交互图和模块依赖图三个切换页签。

### 10.5 里程碑 V：交付计划

主要视图：纵向切片交付图。

必须展示：

- 切片顺序和依赖；
- 每个切片提供的业务价值和真实消费者；
- 验收标准、模型元素、生产代码、测试和验证命令；
- 切片当前状态；
- 独立 Git 提交和回滚点；
- OpenSpec Proposal、Spec、Design、Tasks 与切片的对应关系。

建议形式：切片 DAG 加交付追踪矩阵。已经完成、当前实施、阻塞和未开始的切片应具有不同状态。

### 10.6 里程碑 VI：最终验收

主要视图：从用户场景到运行证据的覆盖矩阵。

必须展示：

- 已交付与未交付范围；
- 场景、验收标准、真实消费者、生产代码、测试、运行结果和 Git Commit；
- 模型元素和不变量覆盖率；
- 架构依赖、Published Language 和循环依赖检查；
- 必需测试层级、E2E、兼容性和重构前后行为对比；
- OpenSpec 严格校验、正式 Spec 合并和归档状态；
- 遗留风险和后续 change 建议。

建议形式：覆盖热力图、证据状态表和最终结论卡片。

## 11. “当前确定内容”的表达规则

控制面板不得把候选内容显示为已决定事实。所有节点和结论必须带有成熟度状态：

| 状态 | 含义 | 展示方式 |
|---|---|---|
| Fact | 有代码、测试、运行或人工输入支持的现状事实 | 实线、普通底色 |
| Hypothesis | 尚待验证的解释 | 虚线、灰色 |
| Candidate | 事件风暴发现的候选边界或模型 | 虚线、蓝灰色 |
| Proposed | 等待当前里程碑人工批准的方案 | 黄色标记 |
| Approved | 已被人工批准的业务或设计决定 | 绿色标记 |
| Implemented | 已有代码实现证据 | 蓝绿色标记 |
| Verified | 已通过测试和运行证据 | 深绿色标记 |
| Blocked | 因未决问题或证据不足不能继续 | 红色标记 |

可视化只投影持久化状态。不得调用 LLM 补全缺少的节点或关系。

## 12. 人工审核交互

### 12.1 可用操作

当且仅当里程碑状态为 `awaiting_review` 时显示：

- `批准`；
- `要求修改`；
- `拒绝`。

### 12.2 操作约束

1. 所有审核操作必须调用现有 lifecycle review 事务；
2. 控制面板不得直接修改 `workflow-state.json` 或正式里程碑 Markdown；
3. `批准` 前显示确认对话框，并列出本次将被确认的决定；
4. `要求修改` 必须填写具体反馈；
5. `拒绝` 必须填写原因；
6. 状态机拒绝操作时，面板展示原始门禁原因，不进行自动降级；
7. 已完成或归档 workflow 只读；
8. 审核成功后立即刷新时间线和下一步动作。

## 13. 数据来源与一致性

### 13.1 Workflow 发现范围

面板只扫描当前项目中的两个有界目录：

```text
openspec/changes/*/ddd/.ddd/workflow-state.json
openspec/changes/archive/*/ddd/.ddd/workflow-state.json
```

同时兼容 archive 下带日期前缀的 change 目录。

### 13.2 数据优先级

1. `workflow-state.json`：工作流状态、当前阶段、审核结果和下一步；
2. 阶段事务中的结构化投影：事件、上下文、聚合、切片和证据关系；
3. I 至 VI 正式里程碑文档：面向人的完整正文；
4. OpenSpec metadata、tasks 和 archive 状态；
5. Git 和验证证据。

状态发生冲突时必须显示“一致性异常”，不得自行选择一个看似合理的结果。

### 13.3 历史 workflow 兼容

已有历史 change 可能只有 Markdown，没有足够的结构化图数据。此时：

- 仍展示 workflow、状态、正式文档和审核记录；
- 能可靠恢复的结构才进入图；
- 不能恢复时显示“该历史里程碑没有结构化可视化数据”；
- 不使用 LLM 从自然语言猜测图结构。

## 14. 可视化数据合同

为了让可视化稳定，阶段完成事务需要保存只读的展示投影。投影不是新的领域事实来源，而是对同一阶段事务中已校验内容的结构化表达。

每个里程碑投影至少包含：

```text
MilestoneProjection
├── workflowId
├── milestoneRoman
├── status
├── generatedAt
├── sourceCheckpointIds[]
├── nodes[]
│   ├── id
│   ├── type
│   ├── label
│   ├── maturity
│   └── evidenceRefs[]
├── edges[]
│   ├── source
│   ├── target
│   ├── relation
│   └── maturity
├── decisions[]
├── openQuestions[]
└── evidenceSummary
```

要求：

- 节点 ID 在同一 workflow 内稳定；
- 每条已确定关系可以追溯到 checkpoint、人工决定或实现证据；
- 里程碑修订后生成新 projection revision，不覆盖审核历史；
- 控制面板默认显示当前有效 revision，并允许查看历史 revision；
- projection 的生成与正式里程碑发布属于同一阶段事务，避免文档和图不一致。

## 15. SDK 实现边界

### 15.1 SDK 入口

当前插件继续保留服务端入口 `src/index.ts`，并新增 TUI 入口 `src/tui.tsx`：

```text
src/index.ts                    # 生命周期工具、状态机和写入门禁
src/tui.tsx                     # Slash 命令、Route、Dialog 和面板渲染
src/dashboard/discovery.ts      # 活动与归档 workflow 发现
src/dashboard/read-model.ts     # 控制面板只读模型
src/dashboard/projections.ts    # 六里程碑可视化投影
src/dashboard/actions.ts        # 受状态机保护的审核动作
src/dashboard/components/*      # OpenTUI / Solid 组件
```

包需要导出服务端入口和 TUI 入口：

```text
"exports": {
  ".": "./dist/index.js",
  "./tui": "./dist/tui.js"
}
```

### 15.2 SDK 能力使用

- 使用 `@opencode-ai/plugin/tui` 注册 Slash Command；
- 使用 keymap layer 只注册 `/ddd-workflow`；
- 使用 Route 展示独立控制面板；
- 使用 Dialog 完成人工审核确认与修改意见输入；
- 使用主题 Token，适配深色和浅色主题；
- 使用 SDK event 或文件更新事件触发增量刷新；
- 使用本地只读 projection，不把整个 workflow 文档加入模型上下文。

OpenCode 官方的 CLI Plugin 能力已经支持命令、Route、Slot、Dialog、本地存储和 Solid/OpenTUI 组件，因此本需求不需要修改 OpenCode 主程序。参考：[OpenCode CLI Plugin 文档](https://opencode.ai/v2/docs/build/plugins/cli/) 和 [OpenCode SDK 文档](https://opencode.ai/docs/sdk/)。

### 15.3 OpenCode 与 Mobile Coder 兼容

首要验收环境为插件当前依赖的 OpenCode Plugin SDK 版本。Mobile Coder 只有在其宿主加载同一 `./tui` 插件入口并实现所需 Route、keymap 和 Dialog API 时，才启用完整面板。

若宿主只支持服务端插件：

- 保持现有 `/ddd`、`/ddd-code` 和 `ddd_lifecycle` 可用；
- 不注册一个会转成 LLM Prompt 的伪控制面板命令；
- 启动时给出“当前宿主不支持 DDD TUI 控制面板”的一次性提示。

## 16. 性能与非功能要求

| 指标 | 目标 |
|---|---:|
| 打开面板的模型调用 | 0 |
| 打开面板的 Token 消耗 | 0 |
| 50 个 workflow 的首次加载 | ≤ 1 秒 |
| 列表筛选与里程碑切换 | ≤ 100 毫秒 |
| 状态事务完成后的界面刷新 | ≤ 500 毫秒 |
| 单个历史 workflow 损坏时 | 不影响其他 workflow 展示 |
| 支持平台 | Windows、macOS、Linux |

其他要求：

- 键盘可完成全部操作；
- 颜色之外必须提供文本状态；
- 长事件流和 Context Map 支持滚动、缩放或聚焦；
- 面板关闭后返回原会话，不改变 Prompt；
- 不在日志中输出完整业务文档或敏感数据；
- 大型历史库采用增量索引，不在每次按键时重新扫描目录。

## 17. 异常处理

| 异常 | 产品行为 |
|---|---|
| 项目没有 workflow | 展示空状态，并提示使用 `/ddd <需求>` 创建 |
| state JSON 无法读取 | 将该 workflow 标记为“状态损坏”，显示路径和错误 |
| 正式文档缺失 | 显示一致性异常，不根据 state 临时生成正文 |
| workflow ID 重复 | 分别展示活动和归档记录，并标记冲突 |
| 审核事务被状态机拒绝 | 保留原状态并展示 findings |
| projection 版本落后 | 显示“可视化待刷新”，正文仍可阅读 |
| OpenSpec 状态不一致 | 显示活动路径、归档路径和 state 三方对比 |

## 18. 验收标准

### 18.1 Workflow 发现

- [ ] `/ddd-workflow` 可以直接打开 SDK 原生全屏控制面板；
- [ ] `/ddd-workflow` 不接收命令参数，也不依赖参数完成导航；
- [ ] 能同时发现活动 change 和 archive 中的 workflow；
- [ ] 新增功能、系统重构、新建系统三种 workflow 均能正确显示；
- [ ] 列表状态与 `workflow-state.json` 一致；
- [ ] 关闭面板不会向会话提交 Prompt。

### 18.2 里程碑展示

- [ ] 所有 workflow 固定展示 I 至 VI 六个里程碑；
- [ ] 当前阶段、待审核状态和已批准状态准确；
- [ ] I 展示战略事件流；
- [ ] II 展示子域、限界上下文和 Context Map；
- [ ] III 展示战术事件流；
- [ ] IV 展示应用服务、聚合和模块依赖；
- [ ] V 展示纵向切片与交付追踪；
- [ ] VI 展示实现、测试、Git、回滚和归档证据；
- [ ] 候选内容不会被显示成已批准结论。

### 18.3 人工审核

- [ ] 只有待审核里程碑显示审核操作；
- [ ] 批准、修改和拒绝均经过确认；
- [ ] 审核动作只能通过 lifecycle review 事务；
- [ ] UI 无法绕过状态机、直接修改正式 Markdown 或 state；
- [ ] 审核完成后状态和可视化自动刷新。

### 18.4 性能与兼容

- [ ] 打开和浏览控制面板不会产生模型 Token；
- [ ] 50 个 workflow 的首次加载不超过 1 秒；
- [ ] 单个损坏的历史 workflow 不会导致面板崩溃；
- [ ] OpenCode 深色与浅色主题均可读；
- [ ] 不支持 TUI Plugin API 的宿主能够安全降级。

## 20. 成功指标

- 用户找到“当前等待审核的里程碑”的时间小于 10 秒；
- 90% 以上的人工审核可以从控制面板完成；
- 因误读 workflow 当前阶段产生的错误操作降为 0；
- 浏览状态相对于 Prompt 生成报告节省 100% 模型 Token；
- 可视化中的已批准节点与持久化人工决定一致率达到 100%；
- 控制面板操作绕过状态机的次数为 0。

## 21. 待确认产品决策

1. MVP 是否同时支持人工审核操作，还是首版只读；
2. 历史 workflow 的 Markdown 是否需要一次性迁移为结构化 projection；
3. Mobile Coder 是否作为 MVP 的强制验收宿主。

## 22. 推荐方案

采用 `/ddd-workflow` 作为唯一入口，执行后直接进入全屏 TUI Route。首版同时提供只读浏览和受状态机保护的人工审核；搜索、筛选、workflow 切换和里程碑导航全部在面板内部完成。可视化数据应由阶段事务同步产生结构化 projection，不采用运行时 Markdown 正则解析，更不调用 LLM 临时生成图。

推荐先完成里程碑 I、II，因为战略事件流、子域和限界上下文最能解决当前人工审核的阅读成本；随后再补齐战术设计、纵向切片和最终证据视图。
