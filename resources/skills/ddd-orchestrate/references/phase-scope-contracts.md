# DDD 阶段 Scope 合同

每个阶段只解决一种专业问题。Scope 只定义观察层级；同一 Scope 内仍可能包含多个职责不同的阶段。每个实际 stage 的唯一问题、允许工件类型、证据义务和唯一输出以 [stage-intrinsic-contracts.json](stage-intrinsic-contracts.json) 为准。

| Scope ID | 观察尺度 | 唯一问题 | 允许决定 | 禁止决定 | 输出给谁 |
|---|---|---|---|---|---|
| `request-routing` | 用户意图、仓库状态与三条互斥工作流 | 本次请求应进入哪一条且仅哪一条工作流？ | 请求意图、仓库是否已有生产行为、互斥路由及升级条件 | 领域事件、边界、模型、切片和代码 | 已选择工作流的首个业务输入阶段 |
| `refactor-scope-convergence` | 现有项目的业务入口、真实消费者路径与项目级重构意图 | 这个宏大或模糊的重构诉求，本轮究竟要解决哪条有业务价值且可验收的端到端问题？ | 项目级愿景、本轮目标/非目标、保留行为、候选业务切面、候选评分、推荐试点切面、本轮完成与项目完成的不同口径 | 子域分类、限界上下文定稿、模块/微服务部署、聚合、类、表、迁移切片和生产代码 | `existing-system-baseline` |

### 新增功能的意图完整性

`add-feature` 进入 `system-discovery` 时，必须把事件源、命令、生命周期动作和外部能力标为 `现状已存在`、`本次目标` 或 `未来候选`。现状标签需要仓库、运行行为、正式 Spec 或历史决策证据；本次目标必须直接服务用户原始结果；其他有价值但缺少依据的能力只能进入未来候选。未来候选未经里程碑 I 人工明确批准，不得进入主流程、基础交付、验收标准或后续战术输入。

## 强制阶段声明

每个阶段开始时先执行 `begin-stage`。AI 只能修改 `.ddd/workbench/<stage-id>/` 下的候选稿与机器工件，不能直接修改正式罗马数字里程碑文档。阶段开始时必须明确唯一问题、已批准输入、允许工件类型、证据义务和唯一输出，并在候选稿隐藏标记区写入：

```text
<!-- ddd-scope:<Scope ID> -->
```

不要把内部 Scope 声明写成人类文档的可见标题。阶段边界应体现在固定业务章节的实际内容中；需要说明不适用时写明业务原因，不能通过删除固定章节规避阶段责任。

候选稿提交前必须形成 `ddd-stage-output/v3` 和由独立 Scope 审查轮次生成的 `ddd-scope-review/v3`。每条 active item 必须声明实际责任步骤、内禀契约、决策层级、成熟度、固定业务章节和当前阶段要求的语义属性；`relations[]` 必须表达命令、事件、读模型、策略、未决问题与证据的真实关系；`soleOutput.itemRefs` 只能引用当前 active item。每条 item statement 必须逐字进入其声明的固定业务章节，使结构化工件成为 Markdown 的事实源。下游想法必须作为 `deferredItems` 指向当前工作流中明确的后续步骤。审查轮次逐条引用 active item、语义关系、唯一输出和所有变更章节，只报告责任判断、处置、严重度和理由，不得填写总体验收结论。`checkpoint` 绑定候选稿及阶段工件哈希，并由程序计算最终 Scope gate。只有程序计算为 `pass`，候选稿才会发布为正式里程碑；失败时正式文档、状态和 checkpoint 数量保持不变。

结构化语义图还必须满足以下不变量：未决问题通过 `blocks` 指出受影响结论，被阻塞内容不得进入主流程、本次目标或唯一输出；查询命令通过 `returns` 产生读模型，状态改变命令通过 `emits` 产生真实领域事件；外部参与方必须证明位于当前系统边界之外；现状能力只能由 operational 且至少 statically-reachable 的事实证明；候选、未来能力和 AI 推荐不得冒充用户请求或既有人工批准。

当前步骤只能修改其内禀契约的 `ownedSections`；只有该里程碑最后一个 `humanGate: true` 步骤可以刷新 `一页结论` 与 `本次请您确认`。人工批准前的新结论只能是事实、假设、候选或拟议状态，AI 不得自行写为 `approved`，也不得使用“已确认纳入本次变更”“最终确定”等措辞代替审批。

## 越界处理

- 上游信息不足：回到上游，不在本阶段猜测。
- 发现下游问题：记录为约束或候选，不越级定稿。
- 独立 Scope Review 发现越权：保留真实责任步骤并使用 `defer`、`remove` 或 `return-upstream`；程序必须判定本次候选稿为 `fail`，修订并重新冻结后再审查。
- Coding 发现模型冲突：停止该切片，回到拥有该决策的战略或战术阶段；后续检查点标记为 `superseded`。
- 评审发现缺口：指出唯一回溯阶段，不在评审章节中暗中重做设计。
