# DDD Model Review

先阅读 `../ddd-orchestrate/references/phase-scope-contracts.md`。实施前评审属于 `context-tactical-design`，只审核并修正 `IV-tactical-design.md` 的战术模型；最终评审属于 `acceptance-evidence`，只核验 `VI-final-acceptance.md` 中真实代码、测试、运行和 Git 证据。评审不得暗中替代战略设计、战术设计或 Coding；发现越界问题时必须回退到拥有该决定的阶段。

最终评审还必须核对同名 OpenSpec change：所有 tasks 已完成、Requirement/Scenario 与批准的 DDD 用例和不变量一致、严格校验通过。最终批准后由 `ddd-openspec-bridge` archive；archive 失败时不得判定工作流完成。

> 🌐 English version: [English](SKILL.en.md)

## 使用时机

- 战术建模完成后，需要对整体模型做质量门禁检查。
- 已有建模工件需要全面评估（可作为独立入口使用）。
- 定期模型健康检查：团队希望量化模型质量并识别退化趋势。

## 输入要求

- **必需**：工作流实施就绪评审必须提供下列完整链路；仅独立健康检查时才允许至少 3 项：
  - 系统用户场景或恢复的 AS-IS 行为
  - 上下文目录与词汇表（来自 `ddd-contexts`）
  - 上下文关系矩阵（来自 `ddd-context-map`）
  - 微服务用例与“系统场景 → 战略职责 → 服务用例”追踪矩阵（来自 `ddd-context-use-cases`）
  - 应用服务与事务编排（来自 `ddd-application-services`）
  - 聚合目录与不变量表（来自 `ddd-aggregates`）
  - 领域事件目录与服务定义（来自 `ddd-domain-interactions`）
  - 持久化、迁移与可靠消息设计（来自 `ddd-persistence-design`）
- **可选**：子域分类（来自 `ddd-subdomains`）、事件流（来自 `ddd-discover`）、scope 定义（来自 `ddd-scope`）。

实施前评审还必须输入公开契约/方法签名、验收标准、实现文件映射和测试场景；最终评审必须额外输入 Git 精确范围、生产代码、测试结果、运行证据、兼容性和回滚证据。

## 流程

1. **术语一致性检查**：扫描所有工件中的术语使用，检测跨工件的命名冲突、定义漂移、同名不同义。
   - **行业对标（可选但推荐）**：若业务域存在成熟的开源参考实现（如物流域 Cargo、电商域 Broadleaf、B2B 域 Pyramid），应将其作为第 9 维比对参考。逐条列出：本模型对参考的 **语义融合/拆分偏离**；参考 **已知局限的主动识别**（例如 Activity/Status/Event 重叠）；**未建模但应考虑的未来域**（例如 Billing/Customer/Carrier）。
2. **边界一致性检查**：验证聚合边界是否与上下文边界一致——不变量不应跨越上下文。
3. **完整性检查**：核对事件流中的每个事件是否在事件目录中有正式定义；每个命令是否有对应聚合处理。
4. **耦合分析**：评估上下文间耦合度——依赖方向、共享数据量、同步调用数。
5. **纵向追踪检查**：验证系统场景 → Big Picture 事件 → 战略职责/服务边界 → 服务用例 → Design-Level 命令/事件 → 应用服务 → 聚合/领域服务 → 持久化与真实消费者可双向追踪。
6. **职责分层检查**：验证应用服务只负责编排、业务规则由领域模型承载、持久化不反向决定聚合边界。
7. **评分**：对以下维度 0-10 评分：术语一致性、边界合理性、场景追踪率、不变量表达率、事件完整性、职责分离、持久化契合度、耦合度；若启用了行业对标，追加 "对标偏离" 维度。
8. **问题清单与回溯触发**：输出发现的问题、影响、证据、建议修复方案，并按触发条件生成回溯指令。
9. **工程就绪检查**：逐项核对公开契约、方法签名、仓储语义、持久化查询/迁移、验收测试和实现文件映射；缺一项即列为阻塞项。
10. **代码交付检查**：最终评审校验 `ddd-implementation-evidence/v2`、`baselineSha..implementationSha`、真实消费者、生产代码、变更测试、通过的验证命令和回滚命令。文档或状态机标记不能作为实现证据。
11. **设计—代码与架构一致性检查**：对所有启用 `designConformanceContract` 的工作流读取 `model-contract.json` 和 `../ddd-orchestrate/references/implementation-conformance-contract.md`，逐项核对批准的 `ME-*`/`INV-*`、模块/层归属、专用生产/测试路径、依赖方向、Published Language、循环依赖与实现证据。实施前阻止候选措辞、无归属不变量、模糊目录约定和脚本式 Service 降级；最终评审要求模型覆盖率 100%、偏离为空、依赖扫描通过。新增与新建使用严格模式；重构只允许具有基线证据和移除切片的精确遗留例外，且不得扩大。
12. **里程碑 VI 测试验收**：只在 `acceptance-evidence` Scope 内核验四项硬结论：全部已交付 AC/INV 均有通过的测试映射；本切片必需的 domain/application/integration/architecture/E2E 层级以及适用的 contract/characterization 层级均通过；E2E 覆盖全部真实 consumer 且没有用 mock 替代业务路径；`refactor-system` 在 baseline 与 implementation 上运行相同验收场景且无未批准差异。新增与新建明确记录“重构前后行为对比：不适用”。任一项缺失时结论必须为 `Not Ready`，不得 archive。

## 输出

| 工件         | 结构要求                                                                                         |
| :----------- | :----------------------------------------------------------------------------------------------- |
| 评分总览     | 表格：维度（术语一致性、边界合理性、不变量表达率、事件完整性、耦合度）、得分(0-10)、主要扣分原因 |
| 问题清单     | 表格：问题、影响、证据（引用具体工件）、建议修复、优先级                                         |
| 行业对标报告 | （仅当启用）表格：对比项、参考实现做法、本模型做法、是融合/拆分/遗漏、是否可接受、建议           |
| 回溯触发清单 | 表格：触发条件、回溯目标 Skill、说明                                                             |
| 实施就绪判定 | 结论：`Ready` / `Not Ready` + 阻塞项列表；只有 `Ready` 才能进入路线图                               |
| 实现证据审计 | 最终评审表格：AC/INV 测试覆盖、必需测试层级、真实 E2E、重构前后行为对比（适用时）、消费者、生产/测试路径、验证命令、Commit SHA、兼容与回滚 |

## 校验清单

- [ ] 每个扣分项都提供可复核的证据（引用具体工件与条目）
- [ ] 回溯触发条件明确且可执行
- [ ] 评分可重复（相同输入得到相同分数）
- [ ] 实施就绪判定有明确的通过/不通过标准
- [ ] 若业务域存在公认的开源参考实现，已至少做过一轮对标；对标结论已沉淀到问题清单
- [ ] 实施前评审已给出唯一明确的 `实施就绪判定：Ready` 或 `Not Ready`
- [ ] `Ready` 时阻塞项为零，且契约、签名、测试、文件映射均可直接执行
- [ ] 最终评审未把文档、空章节、工作流状态或自动批准当作代码实现证据
- [ ] 里程碑 VI 已证明测试覆盖完整、必需测试层级通过、E2E 真实链路通过；重构分支还已证明前后行为对比通过

## 回溯触发

本 Skill 是反馈闭环的核心触发器。根据评估结果触发以下回溯：

| 触发条件                   | 回溯至                    | 说明                             |
| :------------------------- | :------------------------ | :------------------------------- |
| 聚合边界与上下文边界矛盾   | `ddd-contexts`            | 上下文需重新划分以容纳一致性需求 |
| 术语冲突率 > 20%           | `ddd-contexts`            | 通用语言定义不充分               |
| 不变量表达率 < 60%         | `ddd-aggregates`          | 聚合可能为数据容器而非行为边界   |
| 集成模式与上下文映射不一致 | `ddd-context-map`         | 战术层发现了新的集成需求         |
| 事件完整性 < 70%           | `ddd-domain-interactions` | 事件目录缺失或未覆盖关键流程     |

**防止无限循环**：同一回溯路径最多执行 3 次。若第 3 次仍触发，标记为"需人工介入的架构决策"。
