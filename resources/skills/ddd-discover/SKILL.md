# DDD Discover

EventStorming 是发现方法，不等于“战略设计”或“战术设计”本身。必须先阅读 `../ddd-orchestrate/references/phase-scope-contracts.md`，声明且只执行一种格式。

## `big-picture`

- **时序**：系统级用户场景批准后、子域/限界上下文/微服务划分前。
- **输入**：整个系统的用户场景；现有系统可同时输入从代码、数据、测试和运行行为恢复的 AS-IS 流程。
- **范围**：端到端核心流程，可跨越多个候选子系统、限界上下文、团队和外部系统。
- **发现目标**：领域事件时间线、核心流程、参与者、命令、策略、外部系统、异常/补偿、热点、事件聚类、职责与边界线索。
- **消费者**：`ddd-subdomains`、`ddd-contexts`、`ddd-context-map`。
- **隐藏 Scope 标记**：`<!-- ddd-scope:system-discovery -->`；正文只填写里程碑 I 的固定业务章节。
- **禁止**：在此阶段确定子域/限界上下文/部署边界，或直接确定聚合、仓储、应用服务类、表结构和代码文件。事件聚类只能称为职责或边界“线索”。

把事件时间线、核心流程、跨边界事件流、职责候选和热点写入 `I-strategic-eventstorm.md`。可保留内部分析快照，但不为用户生成多个阅读入口。

完成后必须作为战略事件风暴卡点展示给用户。除当前事件流外，还要提供遗漏场景、事件聚类、职责划分和未来能力演进的候选建议，说明各自依据、风险和推荐方向。不得只给出满足当前需求的最小事件链。

必须使用明确图例区分：参与者、命令、过去时领域事件、策略/业务规则、读模型、外部系统、时间触发器、失败/补偿和热点。同步在 `stage-output.json` 中用结构化关系表达：改变状态的命令以 `emits` 指向领域事件，信息查询以 `returns` 指向读模型，事件以 `triggers` 指向真正受它驱动的策略，未决问题以 `blocks` 指向受影响结论。不得把“接口已调用”“列表已返回”“数据已写入”“用户看到了结果”等技术动作或通用应用结果冒充领域事件。领域事件必须说明哪个业务主体的什么状态发生变化，或者确实触发了哪个后续业务策略；查询所得列表、聚合视图和日期过滤结果属于读模型或业务规则。只对当前场景有证据或确有必要的顺序、可见性、状态、权限、幂等与恢复语义给出结论、候选方案或明确待决项，不得从其他业务套用问题清单。责任聚类只能命名为“身份验证职责线索”“轨迹形成职责线索”等业务线索，不能提前写成“某某上下文”或 `BC-CAND-*`。

把技术现象翻译回业务语义后再进入 Big Picture 主体。例如，把“Redis TTL 在零点过期”写为“跨自然日后昨日记录不再进入今日结果”；把“SETNX 或唯一索引”写为“同一业务主体重复提交时必须得到一致业务结果，技术手段延期到战术设计”；把“返回 HTTP 409”写为“重复提交被拒绝并返回可理解的业务结果”。Controller、Service、Mapper、DTO、表、索引、缓存算法和代码路径只能在证据索引中证明现状，不能成为事件流、业务策略、热点方案或当前推荐。

现有系统的新增功能还必须保护需求意图。将事件源、命令、生命周期动作和外部能力明确标为 `现状已存在`、`本次目标` 或 `未来候选`，并在 `stage-output.json` 用稳定 `capabilityId`、`existing|target|future`、`scopeDisposition`、`flowRole`、`authorityRefs` 与 `sourceFactRefs` 同步表达。`existing` 必须引用一个已发布、原子、可运行且至少能从真实消费者静态到达的现状事实；类、常量、空接口、TODO 和桩只能证明结构存在，不能证明能力存在。`target` 必须来自 `user-input:` 或此前 `approval:`；AI 推荐的前置能力在人工扩大范围前仍是候选。EventStorming 可以发现邻接能力，但当前代码、运行行为、正式 Spec、历史决策和用户请求均未提供的能力默认是 `future`，只能进入演进建议，不得进入主流程、唯一输出、基础交付或验收标准，直到人工明确扩大范围。

不得一边把某项语义写入主流程、目标能力或读模型，一边又把它列为“待确认”。每个未决 `open-question` 必须通过 `blocks` 精确关联受影响条目；受阻条目只能保留为备选或从当前候选稿移除。外部系统必须拥有当前系统边界之外的所有权或契约证据；同一单体内部的店铺、用户、订单等既有能力只是内部相邻能力或责任线索。自然日、超时等时间语义使用 `time-trigger`，不能为了填图例把它伪装成外部系统。

## `design-level`

- **时序**：战略设计和实现单元用例包批准后、战术设计前。
- **输入**：一个已选实现单元、其承载的限界上下文职责、通用语言、用例、边界契约与数据所有权。
- **范围**：严格限制在该实现单元及其限界上下文内部；跨单元交互只以输入/输出契约出现。
- **发现目标**：用例流程、应用命令、领域事件、策略、读模型、外部系统、异常/补偿、不变量和事务热点，并给出应用服务、领域服务、聚合及存储需求的候选线索。
- **消费者**：`ddd-application-services`、`ddd-aggregates`、`ddd-domain-interactions`、`ddd-persistence-design`。
- **隐藏 Scope 标记**：`<!-- ddd-scope:context-discovery -->`；正文只填写里程碑 III 的固定业务章节。
- **禁止**：把战略级集成事件直接当成内部领域事件，从现有表结构反推领域模型，或在发现阶段最终确定聚合、服务、仓储、Schema、框架和代码文件。所有模型只可标记为候选。

把服务级事件风暴、命令/策略/读模型、不变量候选和持久化热点写入独立的 `III-tactical-eventstorm.md`。内部快照可以拆分，用户验收入口不能拆分。

这是战术设计前的强制独立 checkpoint 和人工卡点，不是战术设计中的可选分析。完成并持久化该章节、由用户看过当前结果后，才能调用应用服务、聚合、领域交互和持久化设计 skill。不得在同一个未留痕动作中同时生成 Design-Level EventStorming 和最终战术模型。

展示时至少比较两种有意义的不变量归属、聚合边界或一致性候选方案，给出适用条件、代价、风险、扩展能力和推荐理由。不得把“模型最少、对象最少、改动最少”当作默认最优解。

为每个已批准验收标准给出一条可追踪链：

```text
验收标准 → 应用命令 → 业务规则/策略 → 领域事件或拒绝结果 → 读模型/对外结果
```

同时输出失败矩阵：失败条件、业务错误、是否落库、事务效果、幂等/重试、补偿和可观察证据。明确并发竞争、唯一性、排序、分页游标/页码语义、事务边界候选和存储热点；禁止把这些决定全部推迟到 Coding。

## 共同步骤

1. 用过去时列出领域事件，覆盖至少一条主路径和两条异常、回滚或补偿路径。
2. 补充触发命令、参与者、策略、时间触发器、外部系统和必要读模型。
3. 按时间线排序，标注并发、幂等、合规、性能、强一致性和跨系统热点。
4. 记录术语、所有权和状态歧义，并为每项指定需要确认的人。
5. 生成当前格式规定的消费者输入，不越级做下一阶段的决定。

## 强制输入输出链

```text
系统级用户场景
→ Big Picture EventStorming
→ 战略设计：子域、子系统、限界上下文、部署映射、跨边界事件与职责
→ 每个已选实现单元的用例需求
→ Design-Level EventStorming
→ 战术设计：应用服务、领域服务、领域模型、持久化
```

如果 `design-level` 发现一个业务不变量必须跨越多个限界上下文或实现单元同步维护，停止战术设计，返回战略阶段修正边界或一致性策略。
